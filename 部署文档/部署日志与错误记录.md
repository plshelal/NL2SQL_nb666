## 错误记录

### 错误 #1：uv sync 无法初始化缓存目录

- **时间**：部署步骤 2（首次执行）
- **命令**：`uv sync`
- **报错信息**：
  ```
  error: Failed to initialize cache at `C:\Users\Lenovo\AppData\Local\uv\cache`
  Caused by: failed to open file `C:\Users\Lenovo\AppData\Local\uv\cache\sdists-v9\.git`: 拒绝访问。 (os error 5)
  ```
- **原因分析**：uv 默认缓存目录位于系统用户目录 `C:\Users\Lenovo\AppData\Local\uv\cache`。本部署在受限文件沙箱（workspace-write）下执行，沙箱仅允许写入工作区目录，uv 无法在 AppData 下创建/写入缓存文件。
- **解决方法**：将 uv 的缓存目录与 Python 安装目录重定向到工作区内：
  ```powershell
  $env:UV_CACHE_DIR = "<工作区>\.uv-cache"
  $env:UV_PYTHON_INSTALL_DIR = "<工作区>\.uv-python"
  uv sync
  ```
- **结果**：✅ 已解决（缓存目录重定向后 151 个包正常下载）。
- **备注**：该错误为**部署环境限制所致，非 README/项目缺陷**。正常用户机器（非沙箱）直接执行 `uv sync` 不受影响。

### 错误 #2：antlr4-python3-runtime 4.9.3 源码构建失败（PermissionError）

- **时间**：部署步骤 2（uv sync 第二次执行）
- **命令**：`uv sync`（UV_CACHE_DIR 已重定向到工作区）
- **报错信息**（节选）：
  ```
  × Failed to build `antlr4-python3-runtime==4.9.3`
  ╰─▶ Call to `setuptools.build_meta:__legacy__.build_wheel` failed (exit code: 1)
  PermissionError: [Errno 13] Permission denied: '...\.uv-cache\builds-v0\.tmpI9580E\.tmp-03s46bdx\antlr4_python3_runtime-4.9.3-py3-none-any.whl'
  PermissionError: [WinError 5] 拒绝访问。: '...\.uv-cache\builds-v0\.tmpI9580E\.tmp-03s46bdx'
  hint: `antlr4-python3-runtime` (v4.9.3) was included because `finance-data` (v0.1.0) depends on `omegaconf` (v2.3.1)
        which depends on `antlr4-python3-runtime`
  ```
- **原因分析**：
  1. `antlr4-python3-runtime 4.9.3`（2021 年老版本，由 omegaconf 2.3.1 传递依赖）在 PyPI 上**无预编译 wheel，只有 sdist**，uv 必须用 setuptools 现场构建；
  2. 构建 wheel 写入 uv 缓存目录的临时子目录时触发 `PermissionError [WinError 5]`——受限文件沙箱（workspace-write）对构建子进程（python/setuptools 写 wheel 文件）的文件操作存在额外限制。
- **解决方法**：清理可能残留损坏权限的 `.uv-cache` 目录，并以完全文件访问权限重跑 `uv sync`。
- **结果**：✅ 已解决（151 个包全部安装，`.venv` 内 fastapi/langchain/langgraph/qdrant_client/sqlalchemy/omegaconf 等核心依赖导入验证通过）。
- **备注**：此为**环境限制 + 老包无 wheel 的叠加问题**，非 README 缺陷。正常用户机器可直接 `uv sync`。

### 错误 #3：TEI 镜像构建失败——清华 PyPI 源不可用

- **时间**：部署步骤 1（Docker 服务构建，TEI 镜像）
- **命令**：`docker compose build tei`（Dockerfile.tei 内 `pip install`）
- **报错信息**：
  ```
  ERROR: Could not find a version that satisfies the requirement fastapi (from versions: none)
  ERROR: No matching distribution found for fastapi
  ```
- **原因分析**：Dockerfile.tei 使用清华 PyPI 镜像源 `pypi.tuna.tsinghua.edu.cn`，该源在容器内返回**空版本列表**（源不可用/异常）。同一构建中 torch CPU wheel（191.8MB）从 download.pytorch.org 下载速度达 6.6MB/s，证明容器网络正常，问题出在清华源本身。
- **解决方法**：修改 `docker/Dockerfile.tei`，将 pip 源从清华源替换为阿里云 PyPI 镜像：
  ```
  --extra-index-url https://pypi.tuna.tsinghua.edu.cn/simple  →  https://mirrors.aliyun.com/pypi/simple/
  pip install -i https://pypi.tuna.tsinghua.edu.cn/simple     →  pip install -i https://mirrors.aliyun.com/pypi/simple/
  ```
- **结果**：已修改，待重新构建验证。
- **备注**：此为**项目依赖的外部源失效**问题（非 README 逻辑错误，但 README 声称"首次构建 5-10 分钟"在源失效时会失败，可靠性受影响）。

### 错误 #5：构建知识索引失败——MetaConfig 缺少 indicator_groups 字段（项目代码 bug）

- **时间**：部署步骤 5（构建知识索引）
- **命令**：`uv run -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml`
- **报错信息**：
  ```
  omegaconf.errors.ConfigKeyError: Key 'indicator_groups' not in 'MetaConfig'
      full_key: indicator_groups
      object_type=MetaConfig
  ```
- **原因分析**：`conf/meta_config.yaml` 包含 `indicator_groups` 配置段（供运行时指标组功能使用），但 `app/conf/meta_config.py` 的 `MetaConfig` 数据类只声明了 `tables` 和 `metrics` 两个字段。`OmegaConf.merge(schema, context)` 合并时，yaml 中的 `indicator_groups` 无法合入结构化 schema → 抛 ConfigKeyError。**这是项目自身代码与配置不一致的 bug**，任何按 README 步骤 5 执行的部署都会在此失败。
- **解决方法**：在 `app/conf/meta_config.py` 中为 `MetaConfig` 补充 `indicator_groups` 字段（新增 `IndicatorGroupConfig` 数据类），保持与 yaml 结构一致：
  ```python
  @dataclass
  class IndicatorGroupConfig:
      name: str
      description: str
      alias: list[str]
      indicators: list[str]

  @dataclass
  class MetaConfig:
      tables: Optional[list[TableConfig]] = None
      metrics: Optional[list[MetricConfig]] = None
      indicator_groups: Optional[list[IndicatorGroupConfig]] = None
  ```
- **结果**：✅ 已修复，重新执行成功（表信息→meta 库、字段向量→Qdrant、字段取值→ES、指标向量→Qdrant 全部完成）。
- **备注**：**README 不可靠点**——步骤 5 的命令在项目原始代码上直接报错，README 未提及此 bug。

### 错误 #7：应用启动失败——conf/finetune_data.json 缺失（README 不可靠点）

- **时间**：部署步骤 7（启动应用）
- **命令**：`uv run -m app.main`
- **报错信息**：
  ```
  FileNotFoundError: [Errno 2] No such file or directory: '...\conf\finetune_data.json'
  ERROR: Application startup failed. Exiting.
  ```
  位置：`app/agent/fewshot_rag.py:23`（lifespan 启动时 `precompute_embeddings()` → `_load_data()`）
- **原因分析**：
  1. README 目录结构声称 `conf/finetune_data.json` 为"Few-shot 示例（启动时自动重建）"；
  2. 实际代码 `fewshot_rag.py` 在启动时**直接 `open(DATA_PATH, "r")` 读取**，不存在"自动重建"逻辑——文件缺失即抛 FileNotFoundError，**应用无法启动**；
  3. 压缩包中只有 `conf/fewshot_embeddings.pkl`（向量缓存），没有 `finetune_data.json`。
- **解决方法**：创建空 JSONL 文件 `conf/finetune_data.json`（该文件是审核通过 Few-shot 规则的回灌入口，空文件 = 空检索池）：
  ```powershell
  New-Item conf\finetune_data.json -ItemType File
  ```
- **结果**：✅ 已创建空文件，应用正常启动。
- **备注**：**README 不可靠点**——README 声称"启动时自动重建"，但代码无重建逻辑，任何首次部署都会因该文件缺失而启动失败。

### 错误 #8：提问无法返回结果——Few-shot 空向量数组维度不匹配崩溃（错误 #7 修复的连锁问题）

- **时间**：部署完成后提问测试
- **现象**：前端提问无结果返回；应用日志显示每次查询在 `generate_sql` 节点崩溃：
  ```
  app.agent.nodes.generate_sql:generate_sql:238 - 生成sql异常: shapes (0,) and (1024,) not aligned: 0 (dim 0) != 1024 (dim 0)
  ```
- **原因分析**（连锁根因）：
  1. 错误 #7 为修复启动崩溃创建了**空 `conf/finetune_data.json`** → `_questions = []`（0 条样本）；
  2. 应用启动时 `precompute_embeddings()` 检测到缓存向量数与样本数不符 → 重新预计算 → 将 `fewshot_embeddings.pkl` 覆盖为**空数组 `shape (0,)`**；
  3. 每次查询时 `generate_sql` 调用 `retrieve_examples()`，其中 `np.dot(_embeddings(0,), query_emb(1024,))` → **维度不匹配崩溃** → 流水线异常 → 返回失败提示（LLM 兜底回答），前端表现为"无法返回结果"。
- **解决方法**：在 `app/agent/fewshot_rag.py` 的 `retrieve_examples()` 中增加空池防御：
  ```python
  if _embeddings is None or len(_embeddings) == 0 or not _questions:
      return []
  ```
  无 few-shot 样本时直接跳过检索（LLM 正常生成 SQL），不再触发空数组点积。
- **验证**：✅ 修复后 SSE 查询（前端实际使用的 `/api/query`）全流程成功，返回真实数据：
  > "A市农商行2025年3月15日各项存款余额为41.22亿元"（chart 值 41.2200 亿元）
- **备注**：此为**项目代码健壮性缺陷**（fewshot_rag.py 未处理空样本池）+ 压缩包缺少 finetune_data.json 的叠加问题。

### 问题 1：添加知识——运算符/字段无法删除、无法排序

- **根因**：删除函数 `delToken()` 一直存在，但 `renderExpr()`/`renderGSel()` 渲染后从不调用 `refreshIcons()`，`<i data-lucide="x">` 始终是空标签，**删除按钮 ✕ 从未显示**（视觉上"无法删除"）。
- **修复**：
  1. 删除按钮改为纯文本 **✕**（不再依赖图标渲染时机），运算符/字段/常数每项可单独删除，悬停提示"删除该元素"；
  2. 新增**拖拽排序**（HTML5 DnD）：按住任意运算符/字段卡片拖动到目标位置即可调整顺序，拖拽中有虚线和半透明反馈；
  3. 指标组构建器的已选指标 chips 同样改为可见 ✕ 删除。

### 问题 2：审核中心——已忽略 tab 看不到被忽略的反馈

- **根因**：`loadReview()` 对已忽略 tab 额外请求 `/api/knowledge/review?status=ignored`，但后端 `list_review` 只接受 pending/approved/rejected → 返回 400 → `rules` 变成 `{detail:...}` 对象 → `rules.map is not a function` 抛异常 → **整个已忽略 tab 渲染失败**。
- **修复**：已忽略 tab 不再请求规则接口（distilled_rules 无 ignored 状态），只加载 `query-review?status=ignored`；并给两个请求都加了数组类型防御。

### 问题 3：审核中心——待审/已生效/已驳回计数恒为 0

- **根因**：`loadCounts()` 只统计蒸馏规则（distilled_rules），不统计用户反馈（query_log），且 `cnt-ignored` 从未赋值。
- **修复**：四个 tab 计数改为 **规则数 + 反馈数** 之和（pending=review+query-review pending，approved=approved+correct，rejected=rejected+problem，ignored=ignored 反馈），侧栏徽标同步；忽略/撤销操作后自动刷新计数（qReview 改用 refreshReview）。

- ✅ 真实后端往返测试：真实反馈 id=7 忽略 → 出现在已忽略列表 → 恢复待审，数据无残留
- ✅ knowledge.html HTTP 200（70KB），拖拽/✕ 标记就位
